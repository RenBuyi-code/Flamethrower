# 加压故障（E1）与泄压故障（E5）逻辑矛盾

## 问题描述

E1（加压故障）和 E5（泄压故障）之间存在逻辑冲突，导致在特定操作场景下出现反直觉的故障显示。

---

## 两路故障的触发条件

### E1 — 加压故障（Pressure Build Fault）

```
触发计时：
  ✓ 油泵运行中
  ✓ 不在喷火状态（fire_active == false）
  ✓ 不在泄压状态（relief_active == false）
  ✓ 压力未达到目标值（pressure < target）

清除条件：
  ✓ 压力达到目标值
```

目的：检测油泵是否正常工作、管路是否堵塞。

### E5 — 泄压故障（Relief Fault）

```
触发计时：
  ✓ 泄压阀开启中（relief_valve_on == true）
  ✓ 压力未降到 5% 以下（pressure > 5%）

清除条件：
  ✓ 压力降到 5% 以下
```

目的：检测泄压阀是否卡滞、管路是否堵塞。

---

## 矛盾场景

### 典型操作流程

```
 1. 操作员发送泄压指令（CH6 进入泄压窗口）
 2. 系统打开泄压阀，油泵停止
 3. E5 触发 ── 压力传感器底噪偏高（>5%），
    即使实际零压力也判定为"泄压不干净"
 4. 系统进入 FAULT 状态
 5. 操作员手动释放残余压力
 6. 系统状态恢复或重新上电
 7. 自检/建压流程启动 ── 油泵开始运转
 8. E1 触发 ── 压力已被放空，油泵转空却压力不涨
 9. 屏幕显示 E1，操作员困惑：
    "我明明是在泄压，为什么报加压故障？"
```

### 问题根源

| 故障 | 系统认知 | 实际情况 |
|------|---------|---------|
| E1 | 油泵转了压力不涨 → 加压系统坏了 | 压力是操作员手动放掉的，不是故障 |
| E5 | 泄压阀开了压力不降 → 泄压系统坏了 | 传感器底噪 >5%，实际已卸空 |

系统不知道"压力是被人为释放的"这个事实。泄压和加压是互逆行为，但在故障管理中被当作独立事件处理，彼此不感知对方的历史。

---

## 影响

- 操作体验：清理完 E5 后紧接着冒出 E1，用户会认为是同一故障没修好
- 现场判断：维修人员分不清是设备坏了还是人为操作导致的
- 售后成本：需要人工解释故障逻辑，否则客户认为系统有 bug

---

## 可能的解决方向

以下方案由客户决策后实施：

### 方案 A：泄压后冷却窗口

E5 清除后，系统进入 N 秒的"泄压恢复期"。在此期间 E1 不触发，给油泵足够时间重新建压。

```
E5 cleared → 启动冷却定时器 N 秒
冷却期内：油泵运转但 E1 不累计计时
冷却到期：E1 恢复正常监控
```

- 优点：改动小，不修改故障管理架构
- 缺点：N 秒设置多少需要现场验证

### 方案 B：E1 排除已知泄压场景

E1 的触发条件增加一条历史记录检测：如果 30 秒内曾发生过 E5，则 E1 不触发。

```
E1 触发计时条件增加：
  最近 30 秒内未发生过 E5
```

- 优点：语义清晰，排除误判
- 缺点：需要引入故障时间戳记录

### 方案 C：故障显示优先级重排

无论 E1 还是 E5，故障发生后在屏幕上同时显示活跃故障清单，而非只显示第一个。

```
当前：E1 + E5 → 只显示 "E1"
建议：E1 + E5 → 循环显示 "E1 E5" 或显示 "E1+E5"
```

- 优点：用户可完整了解当前系统状态
- 缺点：不解决根本矛盾，仅是显示优化

### 方案 D：不做修改（现状接受）

系统严格按照"当前传感器值 + 当前执行器状态"判定故障。操作员手动卸压后重新建压属于操作流程的一部分，E1 在此过程中属于真实报警（系统确实无法建压），操作员应排查油路是否通畅后手动清除。

- 优点：零改动
- 缺点：需要培训操作员理解此逻辑

---

## 建议

**优先推荐方案 A**：改动量最小，不影响现有故障管理架构，对操作体验改善明显。冷却时间建议设为 10~30 秒，具体由现场测试确定。
