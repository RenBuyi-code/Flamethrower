# SlateUI 演进计划

## 1. 目标

SlateUI 的目标不是只做“能显示菜单”的 MCU UI，而是做一个：

- 架构清晰
- 交互顺手
- 可移植
- 可扩展
- 足够轻量
- 展示出来有高级感

当前最重要的方向是建立 **前后台分离能力**，避免 UI 控件、页面逻辑、业务状态彼此直接耦合。

---

## 2. 这里所说的“前后台分离”是什么

在 SlateUI 中，“前后台分离”不是 Web 那种前端/后端，而是：

- **前台（UI Frontend）**
  - 负责页面、控件、焦点、输入响应、动效、渲染
- **后台（App Backend）**
  - 负责设备状态、业务逻辑、参数管理、持久化、控制接口

SlateUI 本身只负责前台能力，不应该直接侵入设备业务。

中间必须存在一层桥接层，把：

- UI 事件
- 菜单动作
- 控件值变化

翻译为：

- 业务调用
- 状态读取
- UI 刷新请求

这层建议命名为：

- `Presenter`
或
- `Controller`

在 MCU 语境下，两者都可以，推荐优先使用 `Presenter`，因为它更强调“把业务状态转成可显示内容”。

---

## 3. SlateUI 推荐分层

### 3.1 Port 层

目录：

- `middleware/SlateUI/port`

职责：

- 屏幕硬件发送
- 输入采样
- 定时/时基支持
- 可选 DMA / 异步发送

约束：

- 只能做硬件抽象
- 不能混入页面、菜单、控件业务

---

### 3.2 Core 层

目录：

- `middleware/SlateUI/core`

职责：

- 事件队列
- 页面管理
- 显存与刷新
- 基础页面生命周期
- 焦点流转基础设施（后续应补）

约束：

- 不直接依赖具体业务
- 不直接依赖 MCU HAL
- 只通过 `port` 与硬件打交道

---

### 3.3 Widgets 层

目录：

- `middleware/SlateUI/widgets`

职责：

- 基础控件
- 基础布局
- 列表控件
- 进度条
- 文本标签
- 参数编辑控件

约束：

- 只负责显示与局部交互
- 不负责业务状态真相
- 不负责跨页面导航策略

---

### 3.4 Menu / Scene 层（建议新增）

建议新增目录：

- `middleware/SlateUI/menu`
或
- `middleware/SlateUI/scene`

职责：

- 菜单数据模型
- 页面描述
- 菜单项类型定义
- action id 映射
- 页面辅助绘制钩子

这一层是 SlateUI 走向“产品级菜单系统”的关键。

---

### 3.5 Presenter / Controller 层（建议放应用侧）

建议放在应用工程，而不是框架核心内部：

- `app/ui_presenters`
或
- `app/ui_controller`

职责：

- 订阅或接收 UI 语义事件
- 调用业务服务接口
- 把后台状态翻译为 UI 状态
- 驱动页面局部刷新

这一层是前后台分离的核心桥梁。

---

### 3.6 Service 层（应用侧）

建议目录：

- `app/services`

职责：

- 参数读写
- 模块控制
- 设备状态查询
- 存储与恢复
- 通信与上报

约束：

- 不依赖具体控件
- 不直接操作 SlateUI 内部结构

---

## 4. 必须坚持的设计原则

### 4.1 控件不是业务对象

不能让这些事情直接发生：

- `Label` 自己去读温度
- `IntEdit` 自己直接改全局参数
- `MenuItem` 自己直接写 Flash
- `ListView` 自己决定业务逻辑跳转

控件应该只负责：

- 显示
- 接收局部输入
- 发出语义事件

---

### 4.2 页面不是后台

页面可以持有：

- 当前选中项
- 滚动偏移
- 编辑临时值
- 动画状态

但页面不应该持有“系统真实业务状态”的唯一副本。

业务真相应该在 Service 层。

---

### 4.3 业务状态与 UI 状态分离

必须区分两类数据：

#### 业务真相数据

例如：

- 当前温度
- 目标温度
- 风扇状态
- 报警标志
- 配置参数

这些由后台服务持有。

#### UI 临时状态数据

例如：

- 当前高亮项
- 当前页滚动位置
- 编辑中的未提交数值
- 动画进度
- 长文本滚动偏移

这些由页面或控件持有。

两者绝不能混在一起。

---

### 4.4 语义事件高于物理按键

不要只围绕：

- 上
- 下
- 左
- 右
- 确认
- 返回

来写整个 UI 逻辑。

更推荐引入 UI 语义事件，例如：

- `SL_UI_EVT_ENTER_ITEM`
- `SL_UI_EVT_BACK`
- `SL_UI_EVT_FOCUS_CHANGED`
- `SL_UI_EVT_VALUE_CHANGED`
- `SL_UI_EVT_VALUE_COMMIT`
- `SL_UI_EVT_ACTION_TRIGGERED`

这样才能把输入方式、中间页面逻辑、后端调用真正解耦。

---

## 5. SlateUI 第一批必须落地的 5 个能力

### 5.1 菜单模型层

目标：

- 用数据结构描述页面、菜单项、参数项、动作项、子菜单项

作用：

- 让 UI 从“手写页面流程”走向“数据驱动”
- 让同一份菜单数据可以切换不同显示形式

不应做重：

- 不做动态分配
- 不做脚本解释器
- 不做复杂反射

---

### 5.2 焦点系统

目标：

- 统一控件焦点、选中、高亮、进入、返回行为

作用：

- 统一编码器、按键、遥控器等输入体验
- 为复杂菜单和未来动画打基础

重点：

- 焦点流转规则必须独立于具体业务

---

### 5.3 轻动效内核

目标：

- 只支持最基本但最有价值的过渡效果

建议只做：

- 位置过渡
- 尺寸过渡
- 滚动偏移过渡

要求：

- 非阻塞
- 固定点或轻量整数实现
- 能与脏矩形/重绘请求配合

---

### 5.4 长文本与长按加速

目标：

- 提升“读起来舒服”和“调参数顺手”这两件最影响观感的体验

建议：

- 文本超宽时自动滚动
- 参数编辑和长列表支持长按加速

价值：

- 成本小
- 用户体感提升非常大

---

### 5.5 页面辅助绘制钩子

目标：

- 页面主体之外，允许附加装饰与上下文信息

适合用来画：

- Logo
- 标题栏
- 侧边图标
- 状态栏
- 页脚提示

价值：

- 非常有利于做“简单但惊艳”的展示效果

---

## 6. 建议新增的关键机制

### 6.1 Widget ID

建议给所有控件增加稳定 `id`，类型建议使用：

- `uint16_t`
或
- `uint32_t`

用途：

- 页面中查找关键控件
- 关联 Presenter
- 生成统一变更事件

建议新增接口：

- `sl_widget_find_by_id(root, id)`

注意：

- `id` 只是定位手段
- 不要把 `find_by_id` 用成全局业务总线

---

### 6.2 控件值变化事件

建议让可编辑控件统一发出变化事件，例如：

- `VALUE_CHANGED`
- `VALUE_COMMIT`

适用控件：

- 整数编辑
- 开关项
- 列表选择项
- 未来的滑块、复选项等

这样 Presenter 就能统一接入。

---

### 6.3 Action ID

建议给菜单动作增加稳定动作编号，例如：

- `SL_ACTION_OPEN_SETTINGS`
- `SL_ACTION_SET_TEMP`
- `SL_ACTION_SAVE_CONFIG`

好处：

- 菜单模型不直接绑定业务实现
- Presenter 能按动作分发到不同服务

---

### 6.4 Page UI State

建议每个页面显式维护自己的 UI 状态结构体，例如：

- 当前索引
- 滚动偏移
- 是否编辑中
- 当前动画状态
- 当前局部刷新需求

不要把这些状态散落在多个控件的内部临时变量里。

---

## 7. 推荐事件流

建议采用如下流转：

1. 输入设备产生原始事件
2. `sl_event_post()` 投递到事件队列
3. `page_manager` 在主循环取出事件
4. 焦点系统决定目标页面/控件
5. 页面或控件发出更高层语义事件
6. Presenter 接到语义事件后调用 Service
7. Service 更新业务状态
8. Presenter 更新 UI state / 请求局部重绘

这条链路一旦建立，SlateUI 就具备真正的前后台分离基础。

---

## 8. 推荐目录演进

建议未来演进为：

- `middleware/SlateUI/core`
- `middleware/SlateUI/widgets`
- `middleware/SlateUI/font`
- `middleware/SlateUI/port`
- `middleware/SlateUI/menu`（建议新增）

应用侧建议：

- `app/services`
- `app/ui_presenters`
- `app/ui_state`
- `app/pages`（如果页面装配逻辑不想完全留在框架内）

---

## 9. 当前阶段不建议做的事

为了保持 MCU 友好，当前阶段明确不建议：

- 做完整双向数据绑定系统
- 做字符串名查找控件
- 做运行时反射
- 做复杂主题脚本系统
- 做依赖动态分配的大型对象树
- 做阻塞式动画
- 让控件直接访问业务模块内部变量

这些都会让框架快速变重，偏离 SlateUI 的方向。

---

## 10. 第一阶段落地顺序（建议）

### 阶段 1：打通分层基础

1. 增加 `widget id`
2. 增加 `find_by_id`
3. 定义 UI 语义事件
4. 给可编辑控件增加 change/commit 事件

### 阶段 2：建立菜单语义层

1. 定义 `menu model`
2. 定义 `action id`
3. 定义菜单项类型
4. 让 `menu page` 与 `list view` 解耦

### 阶段 3：建立前后台桥梁

1. 引入 Presenter/Controller 层
2. 引入 Service 接口约束
3. 页面只持有 UI state
4. 业务状态统一从 Service 获取

### 阶段 4：补体验

1. 长文本滚动
2. 长按加速
3. 页面辅助绘制
4. 轻量动效

### 阶段 5：做展示级 Demo

建议至少做 3 个页面：

- 首页
- 列表设置页
- 参数编辑页

并体现：

- 页面切换
- 焦点高亮
- 值联动
- 局部刷新
- 非阻塞动效

---

## 11. 对 SlateUI 的最终要求

SlateUI 不应只是“一个 OLED 菜单代码集合”，而应该逐步成为：

- 一个轻量、清晰、可移植的 MCU GUI 框架
- 一个能体现产品感的交互系统
- 一个能支撑 Demo，也能支撑真实业务项目的基础设施

如果要做到“简单又惊艳”，关键不是把控件越堆越多，而是做到：

- 分层清楚
- 状态清楚
- 输入清楚
- 渲染清楚
- 业务边界清楚

这才是长期可维护、又有高级感的根本。
